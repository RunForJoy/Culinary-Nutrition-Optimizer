# Исследование рецептов и предсказание рейтингов: сквозной pipeline

Репозиторий содержит финальное промышленное решение задачи препроцессинга текстовых кулинарных данных, подбора моделей машинного обучения для классификации гастрономических рейтингов, интеграции справочников нутриентов USDA и генерации сбалансированного дневного рациона.

### Архитектура проекта и ключевые модули
* **research/nlp_cutting_ingredients_func.ipynb** — исследовательский блокнот лингвистического препроцессинга. Содержит логику парсинга текстовых рецептов через NLP-библиотеку `spaCy` и генерирует эталонный Whitelist кулинарных признаков.
* **research/recipes.ipynb** — основной аналитический блокнот. Содержит сквозной пайплайн, разведочный анализ данных (EDA), этапы валидации моделей, подбор гиперпараметров и сборку ансамбля.
* **src/recipe.py** — объектно-ориентированный модуль бэкенда. Включает класс `RecipeNutritionist` для расчета КБЖУ, предсказания категорий и оптимизации суточного меню.
* **src/nutritionist.py** — консольная программа для инференса. Поддерживает ручной ввод ингредиентов и запуск генератора дневного меню.
* **datasets/** — папка хранения бинарных моделей (`.joblib`), справочников FDA (% DV), конфигураций признаков (`.json`) и пула очищенных рецептов.

### Реализованные инженерные решения

1. **Двухэтапный лингвистический препроцессинг (spaCy & Whitelist)**
В изолированном ноутбуке `nlp_cutting_ingredients_func.ipynb` реализован парсинг сырых текстовых данных. С помощью NLP-модели библиотеки `spaCy` из строк извлечены лемматизированные существительные, очищенные от мусорных мер (веса, объемы) и нерелевантного шума. Географический и календарный спам (названия штатов, сезоны) был отфильтрован автоматически с помощью интеграции библиотеки `pycountry`. В результате 680 исходных признаков были схлопнуты до 334 сильных базовых кулинарных корней. 
Чтобы защитить продакшн-окружение от перегрузки оперативной памяти, библиотека `spaCy` полностью исключена из инференса основного приложения — итоговый слепок признаков зафиксирован в статическом конфигурационном файле `datasets/perfect_ingredient_columns.json`.  

2. **Продуктовая мультиклассификация (История R&D, компромиссы и выбор метрик)**
В основном блокноте `recipes.ipynb` была реализована логика построения моделей машинного обучения:
   * **Отказ от регрессии**: Изначальная попытка предсказывать непрерывный рейтинг выдала высокий базовый шум (`RMSE ~1.20`), что делало продуктовые рекомендации абсолютно хаотичными. Было принято решение перевести задачу в формат стратифицированной мультиклассификации на 3 дискретных класса (`0 - bad`, `1 - so-so`, `2 - great`).
   * **Анализ ловушки изолированного скорера**: В ходе исследования были протестированы альтернативные подходы, зацикленные исключительно на оптимизации одной кастомной метрики `precision` для класса `great` (TP / (TP + FP)). Математический анализ показал, что такой изолированный скорер заводит `GridSearchCV` в тупик на малых фолдах, возвращая штрафные `0.0` при отсутствии срабатываний. Это приводило к сильному переобучению моделей (в частности, базовых деревьев решений), из-за чего они теряли точность на целевом классе и полностью слепли на дефектной еде (всего 25% точности на классе `bad`).
   * **Финальное продакшн-решение**: На очищенной 334-колоночной матрице был применен ансамбль **`VotingClassifier` (с жестким голосованием `hard`)**, объединяющий логистическую регрессию и `LinearSVC`. Для обучения использовался сбалансированный **`precision_macro`**, что заставило модель плавно удерживать и видеть границы всех классов одновременно. Из-за линейной природы алгоритмы прагматично обнулили промежуточный зашумленный класс `so-so` (так как он по ингредиентам кулинарно неотделим от `great`), перенаправив всю математическую мощность на полярные категории.
   * **Итоговый результат**: Данный подход обеспечил тотальное превосходство в метриках. Удалось получить пуленепробиваемый **`Precision Great = 82.27%`** на тесте за счет идеальной чистоты Whitelist-матрицы, и одновременно с этим поднять точность распознавания дефектной и опасной еды (**класс `bad`) до 69%**, что почти в три раза выше первоначальных изолированных моделей.  

3. **Борьба с дубликатами строк**
Для очистки датасета и интеграции истинных рейтингов применено поиндексное слияние с учетом кумулятивного счетчика вхождений повторяющихся названий блюд (обработка дубликатов по тайтлам и отсечение рецептов, содержащих менее 2 ингредиентов). Экстремальные выбросы по калорийности (аномалии свыше 10 000 ккал) были удалены.  

4. **Нутриентный маппинг (FDA / USDA)**  
Сырые данные обогащены расчетом процентов от суточной нормы потребления (% Daily Value). Сбор данных реализован на основе официальных эндпоинтов USDA с фильтрацией по категориям `Foundation Foods`, а отсутствующие в API микронутриенты аппроксимированы по формулам энергетической плотности Этуотера (с вычислением Net Carbs). Итоговая чистая матрица КБЖУ зафиксирована в файле `datasets/nutrients_final.csv`.  

5. **Стохастическая оптимизация меню (Monte Carlo)**
В модуле `src/recipe.py` реализован алгоритм случайного поиска (Monte Carlo) для подбора оптимального дневного рациона (завтрак, обед, ужин). Из пула в 17 241 очищенных рецептов система генерирует комбинации блюд, максимизируя суммарный оригинальный рейтинг и жестко контролируя лимит КБЖУ строго до `100%` от суточной нормы FDA одновременно.  

6. **Реверс-инжиниринг URL-структуры и клиентский парсинг (Sitemap JS-Scraping)**
Прямой массовый сбор живых URL-адресов рецептов через поисковые API привел к жесткой блокировке сетевых запросов механизмами Anti-Scraping (ошибки типа 429 Too Many Requests). Проблема решена двухэтапным обходом ограничений:
* На уровне инференса приложения реализована детерминированная функция генерации slug-адресов вида /recipes/food/views/[slug], работающая в локальной памяти за сотые доли секунды без выполнения внешних сетевых вызовов.
* В качестве основы для масштабирования базы данных, в обход защиты Cloudflare, из браузерной консоли с использованием асинхронного JavaScript-скрипта (с таймаутом 500 мс для предотвращения банов по IP) был выгружен и декомпилирован официальный sitemap-файл технической структуры сайта. Это позволило сформировать эталонный реестр валидных адресов для всей базы рецептов.  


## Инструкция по запуску программы

### Интерактивный веб-интерфейс (Streamlit)

Проект снабжен полноценным графическим веб-приложением на базе фреймворка Streamlit, поддерживающим интерактивный мультиввод, изолированную покомпонентную выдачу нутриентного профиля FDA по каждому ингредиенту (с внутренней сортировкой по убыванию значений) и раскрывающиеся пошаговые инструкции приготовления блюд напрямую из локального JSON-архива.

* **Удаленный доступ (Production)**: Приложение развернуто в облачной инфраструктуре и доступно по прямой ссылке: https://culinary-nutrition-optimizer-fdiepqz62iacuj57eoep2z.streamlit.app/*

* **Локальный запуск интерфейса (Development)**:
  ```bash
  pip install streamlit
  streamlit run app.py
  ```

### Инструкция по запуску программы  в консоли терминала

Перед запуском убедитесь, что создано и активировано виртуальное окружение, установлены зависимости из `requirements.txt` и настроен файл `.env` с ключом `USDA_API_KEY`.

* **Индивидуальный прогноз сочетаемости и КБЖУ по составу продуктов**:
  ```bash
  python nutritionist.py milk, honey, jam
  ```
* **Генерация оптимального сбалансированного меню на день**:
  ```bash
  python nutritionist.py --menu
  ```
  
* **Запуск сквозного автоматического тестирования всей системы**:
  ```bash
  python test_pipeline.py
  ```
  Скрипт в автономном режиме выполняет полную валидацию признакового пространства на отсутствие лингвистического мусора, верифицирует детерминированную категоризацию блюд в пуле рецептов, тестирует работу интерфейсных ограничений Guardrails и проверяет соблюдение жестких суточных лимитов КБЖУ (до 100% от нормы FDA) алгоритмом Монте-Карло.
